### 4.2 YAML 实际结构

以 `addUser.yaml` 为例：

```text
list
└── dict
    ├── baseInfo → dict
    │   ├── api_name
    │   ├── url
    │   ├── method
    │   └── header
    └── testCase → list
        ├── 用例dict 1
        ├── 用例dict 2
        └── 用例dict n
```

`testCase` 不是“一个字典里有多个 case_name”，而是一个列表，列表中的每个字典代表一条独立测试。

### 4.3 `get_testcase_yaml()` 的返回结果

核心逻辑：

```python
base_info = yam_data.get('baseInfo')
for ts in yam_data.get('testCase'):
    param = [base_info, ts]
    testcase_list.append(param)
```

假设有4条用例，返回结构类似：

```python
[
    [base_info, testcase_0],
    [base_info, testcase_1],
    [base_info, testcase_2],
    [base_info, testcase_3],
]
```

pytest 将每一个小列表拆给：

```python
def test_add_user(self, base_info, testcase):
```

因此一个 Python 测试方法会生成多条 Test Item。

### 4.4 原始10条与扩充后12条

## 六、Fixture、登录和动态 Token

### 6.1 自动登录不是参数化用例

`system_login` 的关键属性：

```text
scope=session
autouse=True
```

含义：

- 一次 pytest 会话中，在适用测试首次需要 setup 时最多执行一次；
- 不需要测试方法显式声明参数；
- 不产生单独 Test Item；
- 负责登录并把动态凭证写入根目录 `extract.yaml`。

### 6.2 动态 Token 的使用

正常新增用户中的：

```yaml
token: ${get_extract_data(token)}
```

不是最终 Token，而是动态表达式。执行请求前框架会：

```text
识别 ${...}
→ 调用 get_extract_data("token")
→ 从根目录 extract.yaml 读取实际 Token
→ 替换占位表达式
→ 把 Token 作为表单参数发送
```

其他用例中的：

```yaml
token:
```

经过 `yaml.safe_load()` 后通常是 `None`。这不是“新增失败所以没有产生 Token”，而是该用例故意不读取、不发送有效 Token，用于模拟鉴权失败。

### 6.3 本次运行后 `extract.yaml` 只剩登录数据

完整过程：

```text
clear_extract 清空整个根 extract.yaml
→ system_login 登录
→ 写入 Cookie、CSRF Token 和业务 Token
→ 本次只执行用户模块
→ 没有商品ID、订单号等提取配置
→ 最终只保留本次登录数据
```

## 七、HTTP、业务和pytest三个结果层次

三个层次必须分开：

| 层次 | 示例 | 回答的问题 |
|---|---|---|
| HTTP结果 | `status_code=200` | 服务端是否正常完成本次HTTP请求并返回响应 |
| 业务结果 | `msg_code=9001` | 新增、删除等业务操作是否成功 |
| pytest结果 | `PASSED` | 实际响应是否符合YAML中的预期 |

典型异常用例：

```text
HTTP 200
业务 msg_code=9001
业务消息=新增失败
YAML预期=新增失败
pytest结果=PASSED
```

因此：

> pytest `PASSED` 不等于业务成功；它表示实际结果符合测试预期。异常用例正确返回失败时，测试就应该通过。

HTTP 200 也不只是“网络有连接”。它表示请求在 HTTP 层正常处理并返回；404、500 同样能证明收到了 HTTP 响应，但对应不同的 HTTP 处理结果。

### 10.2 Git状态字母

`git status --short` 使用两列：

```text

```

- 第一列：暂存区状态；
- 第二列：工作区状态。

常见状态：

| 状态 | 含义 |
|---|---|
| `M ` | 已修改并暂存 |
| ` M` | 已修改但未暂存 |
| `A ` | 新文件已暂存 |
| `MM` | 暂存后又继续修改 |
| `??` | 新文件尚未跟踪 |

### 10.3 今日采用的安全流程

```text
git status --short
→ git diff 检查未暂存修改
→ 精确恢复运行态文件
→ 删除明确的缓存和误生成文件
→ git add -- 指定有效文件
→ git diff --cached 检查准备提交内容
→ git commit 保存到本地仓库
```

核心记忆：

```text
git add = 把选中的当前内容放入暂存区
git commit = 把暂存区保存到本地Git历史
git push = 把本地提交上传远程仓库
```

`git clone` 会带来 `.git`、历史、分支和远程地址；下载ZIP通常不含 `.git`。ZIP目录若要变成新仓库应使用 `git init`，不能手工创建 `.git`。

## 十一、SQL事务、锁和隔离级别

### 11.1 事务

事务是一组作为一个工作单元处理的操作：

```text
全部成功 → COMMIT
任意必要步骤失败 → ROLLBACK
```

转账示例：

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE user_id = 'A';

UPDATE accounts
SET balance = balance + 100
WHERE user_id = 'B';

COMMIT;
```

若第二步失败，需要回滚，避免A扣款但B未到账。

事务经常包含多条SQL，但单条SQL在自动提交模式下也可以构成一个事务。

### 11.2 ACID

| 特性 | 含义 | 今日理解 |
|---|---|---|
| Atomicity 原子性 | 全部成功或全部失败 | 防止只完成一半业务步骤 |
| Consistency 一致性 | 从一个合法业务状态进入另一个合法状态 | 转账总额、库存和订单约束保持成立，不是数值前后完全相等 |
| Isolation 隔离性 | 并发事务的中间状态相互隔离 | 控制一个事务能看到其他事务的哪些变化 |
| Durability 持久性 | 提交结果应持久保留 | 服务重启后已提交数据仍存在 |

### 11.3 三种并发异常

```text
脏读：读到其他事务尚未提交、之后可能回滚的数据
不可重复读：同一事务两次读取同一行，值发生变化
幻读：同一事务两次执行同一条件查询，结果记录集合发生变化
```

不可重复读关注“同一行的值”；幻读关注“满足条件的记录集合或行数”。幻读不要求数据库一定使用索引。

### 11.4 四种隔离级别

按标准模型：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| Read Uncommitted | 可能 | 可能 | 可能 |
| Read Committed | 避免 | 可能 | 可能 |
| Repeatable Read | 避免 | 避免 | 可能 |
| Serializable | 避免 | 避免 | 避免 |

隔离越强，并发异常越少，但等待、锁冲突和性能成本通常越高。MySQL InnoDB 的具体表现还会受到MVCC、记录锁、间隙锁和Next-Key Lock影响。

锁主要控制并发访问冲突；隔离级别规定事务可见性。数据库通常结合锁和MVCC实现隔离。

## 十二、算法：LC 543 二叉树的直径

### 12.1 核心关系

辅助函数返回当前子树的最大深度：

```text
depth(node) = max(left_depth, right_depth) + 1
```

经过当前节点的直径：

```text
current_diameter = left_depth + right_depth
```

深度使用从当前节点到叶子的节点数；对于当前节点到子树叶子的边数，左子树深度正好等于从当前节点向左走到最深叶子的边数，因此左右深度可直接相加得到经过当前节点的边数。

最长直径不一定经过整棵树根节点，所以需要在每个节点更新全局最大值。

### 12.2 最终代码

```python
class Solution:
    def diameterOfBinaryTree(self, root: Optional[TreeNode]) -> int:
        answer = 0

        def depth(node):
            nonlocal answer

            if node is None:
                return 0

            left_depth = depth(node.left)
            right_depth = depth(node.right)

            current_diameter = left_depth + right_depth
            answer = max(answer, current_diameter)

            return max(left_depth, right_depth) + 1

        depth(root)
        return answer
```

`depth(root)` 的最外层深度返回值不需要保存，但调用会遍历整棵树并通过 `nonlocal answer` 更新外层直径。递归内部的父节点仍然会接收左右子调用返回的深度。

### 12.3 复杂度

```text
时间复杂度：O(n)，每个节点访问一次
辅助空间复杂度：O(h)，来自递归调用栈
平衡树：O(log n)
退化树最坏：O(n)
```

## 十三、算法：LC 100 相同的树

### 13.1 三个递归出口

```text
p和q都为空 → True
只有一个为空 → False
当前节点值不同 → False
```

当前节点相同后，继续比较对应位置：

```text
p.left 与 q.left
并且
p.right 与 q.right
```

不能写成 `isSameTree(p.left, p.right)`，否则比较的是同一棵树自身的左右子树，并且丢失对q后续结构的判断。

### 13.2 最终代码

```python
class Solution:
    def isSameTree(
        self,
        p: Optional[TreeNode],
        q: Optional[TreeNode]
    ) -> bool:
        if p is None and q is None:
            return True

        if p is None or q is None:
            return False

        if p.val != q.val:
            return False

        return (
            self.isSameTree(p.left, q.left)
            and self.isSameTree(p.right, q.right)
        )
```

### 13.3 复杂度

```text
时间复杂度：O(n)，最坏比较所有对应节点
辅助空间复杂度：O(h)，来自递归调用栈
平衡树：O(log n)
退化树最坏：O(n)
```

### 13.4 何时使用辅助函数

```text
递归子问题的参数和返回值与公开函数完全同形 → 可以直接递归公开函数
递归需要不同参数、不同返回值或额外状态 → 通常使用辅助函数
```

| 题目 | 公开函数 | 递归子问题 | 常见写法 |
|---|---|---|---|
| 最大深度 | 一个节点→深度 | 一个节点→深度 | 直接递归自己 |
| 翻转二叉树 | 一个节点→翻转后的树 | 一个节点→翻转后的树 | 直接递归自己 |
| 相同的树 | 两个节点→布尔值 | 两个节点→布尔值 | 直接递归自己 |
| 对称二叉树 | 一个根→布尔值 | 两个镜像节点→布尔值 | 辅助函数 |
| 二叉树直径 | 一个根→直径 | 一个节点→深度并更新直径 | 辅助函数 |
