## 一、结论

当前用户模块已经能够完成 YAML 参数化、自动登录、动态 Token 替换、HTTP 请求、响应解析和断言，但还不是完整的 CRUD 质量保障：

- 新增接口会向 `userManage.json` 追加数据，具有真实写入副作用；
- 修改接口只比较固定字段，没有修改用户数据；
- 删除接口只判断 ID 是否在固定列表中，没有删除用户数据；
- 查询接口只判断 ID 是否在固定列表中，没有查询 `userManage.json`；
- 修改、删除、查询没有 Token 校验；
- 现有 12 条用例全部通过，只表示实际结果符合 YAML 预期，不表示 12 次业务操作都成功。

## 五、主要覆盖缺口

### 新增用户

1. 缺少 password、dates、phone 的独立缺参用例；
2. username 缺失和 role_id 缺失用例同时缺少 Token，没有隔离变量；
3. 错误 Token、过期 Token、伪造 Token；
4. 手机号长度、非数字手机号、用户名长度、日期格式；
5. 重复用户名或重复请求；
6. 成功后没有查询并验证写入内容；
7. 当前 Mock 只检查真值，不检查格式和业务约束。

### 修改用户

1. 没有缺参、空值、边界、类型错误用例；
2. 没有不存在用户场景；
3. 没有任何鉴权用例；
4. 没有根据用户 ID 更新数据；
5. 没有修改后查询验证；
6. 只要字段与固定字典完全相等就返回成功。

### 删除用户

1. 没有任何鉴权用例；
2. 没有错误类型、超长 ID、负数等边界场景；
3. 没有重复删除的幂等场景；
4. 返回删除成功后没有真正删除；
5. 没有删除后查询验证；
6. 现有断言只检查消息文本，强度不足。

### 查询用户

1. 没有不存在、空值、缺参、类型错误场景；
2. 没有任何鉴权用例；
3. 没有检查错误 HTTP Method；
4. 成功响应没有返回并校验完整用户字段；
5. 查询的是固定 ID 列表，不是 `userManage.json` 中的真实数据。

## 六、已确认的框架与测试设计问题

| 编号 | 问题 | 风险 | 建议阶段 |
|---|---|---|---|
| P-01 | `order=1/2/3/4` 没有对应排序插件 | 执行顺序可能只是源码收集顺序 | 后续依赖治理阶段 |
| P-02 | 四个接口没有围绕同一用户 ID 建立数据链 | 不能证明真实 CRUD 行为 | 业务场景与数据隔离阶段 |
| P-03 | 新增用户直接追加跟踪中的 Mock 数据文件 | 重复运行污染仓库数据 | 数据隔离阶段 |
| P-04 | `extract.yaml` 是共享可变文件 | 并发污染、旧数据残留 | YAML/运行时状态阶段 |
| P-05 | 多条用例只断言消息文本 | 错误码或 HTTP 状态异常可能漏报 | 断言设计阶段 |
| P-06 | 修改、删除、查询没有鉴权 | 未授权请求也可能成功 | 用例扩充阶段 |
| P-07 | Mock 返回成功但不改变最终数据 | pytest 通过不能证明业务真实成功 | Mock 改造阶段 |

## 七、优先级建议

### P0：进入项目 v1 前必须完成

1. 让缺少 username、role_id 的用例使用有效 Token，做到单一变量；
2. 为四个接口统一断言 HTTP 状态码、业务码和消息；
3. 为修改、删除、查询定义并验证鉴权要求；
4. 建立新增返回 ID、查询、修改、删除、删除后再查询的真实数据链；
5. 使用可重置的测试数据，避免直接污染 Git 跟踪文件。

### P1：核心覆盖补充

1. 不存在、空值、缺参、类型和长度边界；
2. 错误 Token、过期 Token和越权；
3. 重复新增、重复删除、重复提交；
4. 修改和删除后的最终状态断言。

### P2：工程化增强

1. 错误 Method、Content-Type 和异常请求体；
2. 并发、数据隔离和幂等；
3. 将运行态数据与仓库初始数据分离；
4. CI 中自动恢复 Mock 数据并保存测试报告。
